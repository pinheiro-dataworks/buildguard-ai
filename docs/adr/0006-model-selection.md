# ADR-0006: Model Selection for the Three Core Tasks

**Status:** Accepted

## Context

Section 14 requires justifying, per task, why each model family was
considered, why the final model was selected, and the trade-offs
(performance vs. complexity, interpretability, inference latency,
operational implications) -- not just picking whatever scores highest.
Section 13 requires every candidate to be measured against the mandatory
baselines, not only against each other. Section 61's rule against padding
the stack means the family list itself needs a reason, not just a
citation of Section 14's menu.

`scripts/train.py` runs this comparison end-to-end on the full synthetic
portfolio (seed 42, `git_sha` `78e0e28`, 400 projects, 345 resolved):
`RandomForestClassifier`/`RandomForestRegressor` and LightGBM, tuned with
Optuna (15 trials, `GroupKFold(3)` on `project_id`) on **train**, compared
against the Section 13 baselines on **calibration** -- **test is untouched**
(Section 12; reserved for the one final evaluation after calibration and
thresholding land, Session I).

## Decision

**Family shortlist: `RandomForestClassifier`/`RandomForestRegressor` and
LightGBM only**, compared against the baselines already built in Session G
(`DummyClassifierBaseline`, `LogisticRegressionBaseline`, `CpiRuleBaseline`;
`MeanRegressionBaseline`, `MedianRegressionBaseline`,
`DeterministicEacBaseline`, `LinearRegressionBaseline`). XGBoost/CatBoost
were not added alongside LightGBM -- see Alternatives.

**Results (calibration split, never touched during tuning):**

| Task | Metric | Dummy/naive | Best other baseline | Random Forest | LightGBM | **Champion** |
|---|---|---|---|---|---|---|
| `cost_overrun` | ROC-AUC (higher better) | 0.500 | 0.888 (logistic) | **0.898** | 0.875 | **Random Forest** |
| `schedule_delay` | ROC-AUC (higher better) | 0.500 | 0.816 (logistic) | 0.940 | **0.974** | **LightGBM** |
| `final_cost` | MAE, $ (lower better) | 14.6M (mean) | 4.96M (linear reg.) | 5.87M | 4.11M | **1.96M -- Deterministic EAC (baseline)** |

**A model won 2 of 3 tasks. A baseline won the third, decisively.** For
`final_cost`, the deterministic EVM Estimate at Completion
(`evm.estimate_at_completion_cpi`, Section 9 -- literally `BAC / CPI`,
zero learned parameters) beats the *tuned* LightGBM regressor by more than
2x (1.96M vs. 4.11M MAE), and beats tuned Random Forest by 3x. This is not
a bug or an undertrained model -- it is a genuine, reproducible finding
(see Session G's baseline validation, which found the same pattern at a
smaller scale) that a domain-informed closed-form formula, fed the same
CPI signal a tree model has to learn indirectly through splits, is
extremely hard to beat on this data. The synthetic generator computes
`forecast_cost` from a project's own current CPI in a way that is close to
mechanically related to its eventual real final cost (`docs/adr/0004-synthetic-data-design.md`),
so this is arguably as much a property of the data-generating process as
of the model -- worth flagging plainly rather than hiding a baseline's win
behind a forced "advanced model" selection.

**Champions actually shipped** (`models/*_champion.joblib`, gitignored,
regenerated by `make train`): `cost_overrun` → Random Forest
(`n_estimators=212, max_depth=14, min_samples_leaf=15`); `schedule_delay`
→ LightGBM (`n_estimators=149, num_leaves=25, learning_rate=0.0148,
min_child_samples=39`); `final_cost` → `DeterministicEacBaseline` (no
parameters to report -- it is the EVM formula itself).

## Trade-offs (Section 14)

| Dimension | Random Forest | LightGBM | Deterministic EAC |
|---|---|---|---|
| Performance here | Best on `cost_overrun` | Best on `schedule_delay` | Best on `final_cost`, by a wide margin |
| Complexity | Medium (ensemble of trees, no learning-rate tuning) | Medium (sequential boosting, more hyperparameters) | None -- one formula |
| Interpretability | Feature importances; SHAP-compatible (Phase 6) | Feature importances; SHAP-compatible | Fully transparent -- the formula *is* the explanation |
| Training latency (this run) | 66s (`cost_overrun`) | 62s (`schedule_delay`), 267s tuning pass on `final_cost` | None (no fitting) |
| Inference latency | Sub-millisecond per row | Sub-millisecond per row | Sub-millisecond per row (arithmetic) |
| Operational risk | Stable, low-variance predictions; larger serialized size | Slightly more prone to overfitting with wide search spaces; smaller serialized size | None -- cannot "fail to converge" or overfit |

None of the three add meaningful inference latency risk against Section
49's p95 < 500ms budget -- all are effectively instant per row. The
practical operational difference is training/tuning time and artifact
size, neither of which matters for a batch-retrained, zero-cost demo
system at this scale.

## Alternatives Considered

- **Also compare XGBoost and/or CatBoost** -- rejected. Section 14 lists
  "LightGBM, XGBoost/CatBoost" as an either/or gradient-boosted-tree
  option, not a mandate to run all three. All three solve the same
  learning problem with the same fundamental approach; adding a second
  boosted-tree library here would cost real tuning time (each family
  already takes 60-270s per task) for a comparison a reviewer could not
  meaningfully act on. LightGBM was kept over XGBoost/CatBoost because it
  was already a declared dependency (`pyproject.toml: ml` extra) with no
  added installation cost.
- **Force an ML model to win every task, e.g. by dropping the
  deterministic EAC baseline from `final_cost`'s comparison** -- rejected
  outright. Section 56 forbids exactly this ("never ... hide" an
  inconvenient result); Section 13's entire point is that a model must
  earn its place against a real baseline, and here it didn't. Shipping the
  baseline as the actual `final_cost` champion is the correct, honest
  outcome of the process this project claims to follow.
  `LinearRegressionBaseline` (Session G) already showed the same qualitative
  pattern at 3.8M vs. 1.6M MAE on a smaller sample -- this run confirms it
  holds at full scale and against genuinely tuned tree ensembles.
  A future session could try to close this gap with a model that receives
  `forecast_cost` as an explicit input feature (it already does -- see
  `NUMERIC_FEATURE_COLUMNS`) plus a residual-learning objective; not
  attempted here to avoid re-deriving a worse version of the EAC formula
  under a different name.
- **Exhaustive grid search instead of Optuna** -- rejected per Section 15
  explicitly ("avoid unjustified exhaustive grids"); Optuna's TPE sampler
  with 15 trials found the reported configurations directly.
- **More CV folds / more trials** -- a larger budget (e.g. `cv_splits=5`,
  `optuna_n_trials=50`) would likely narrow the RF/LightGBM gap slightly
  on `cost_overrun` (0.898 vs. 0.875 is not a wide margin) but was not
  worth the added runtime for a demo-scale project; `configs/base.yaml:
  training.optuna_n_trials`/`cv_splits` are both externalized and easy to
  raise later if warranted.

## Consequences

- Three champion artifacts exist (`models/*_champion.joblib`) and three
  MLflow runs per task are recorded (`sqlite:///mlruns/mlflow.db`,
  experiment `buildguard-ai`), each tagged with `git_sha`, ready for the
  calibration/threshold work in Session I.
- The `final_cost` result means Session I's calibration/uncertainty work
  and any future model card must describe `final_cost` honestly as
  "best current estimate is a deterministic EVM formula, not a learned
  model" -- claiming a fitted regressor "powers" final-cost forecasting
  would misrepresent what is actually deployed.
- `cost_overrun`'s narrow RF-over-baseline margin (0.898 vs. 0.888) is
  worth re-checking once slice evaluation (Section 18, later phase) is
  built -- an aggregate AUC this close can hide a champion that is only
  better on some subgroups.
- `scripts/train.py` regenerates all three champions deterministically
  from `configs/base.yaml` (`make train`); nothing here depends on
  manual steps or un-versioned state.
